# Clade Launcher

Desktop launcher: Tauri 2 (Rust) backend, React + TypeScript + Vite frontend, Tailwind CSS v4, shadcn/ui, pnpm.
Status: UI shell, portable storage, credential vault, runtimes, profile creation, and Microsoft/Xbox/Minecraft sign-in up to Mojang's approval step. Preparing profiles (Minecraft, Java, loaders) and launching the game are implemented; the live end-to-end launch with a real Microsoft account is pending Mojang's approval, and skin/cape changes are not built.

**Hard requirement: the launcher is fully portable.** Read "Portability" below before touching anything that reads, writes or stores a path, a credential, or a setting.

## Localization (PERMANENT): exactly English and Russian
Clade's own UI ships in exactly two languages, **English (`en`) and Russian (`ru`)**. Do not add a third language, a language picker beyond these two, or any machine/network translation. Only the Clade product UI is localized; developer communication, logs, code and comments stay English.
- **Where text lives:** one centralized, in-project layer. `src/locales/en.ts` is the canonical catalog (its keys define the `MessageKey` type), `src/locales/ru.ts` is typed against it (a missing or extra key fails `tsc`), `src/lib/i18n/` is the engine (`core.ts` pure functions: templates, plurals, fallback, first-run resolution; `index.ts` the language store, `t`, `useT`, `useLocale`; `errors.ts` backend errors; `language.ts` the language choice). No user-facing string may be hardcoded in a component, helper or feature module: read it with `t("key", { param })`. Everything ships locally; nothing is fetched.
- **Add a feature = add both languages in the same change.** New text goes into `en.ts` and `ru.ts` together. `i18n.test.ts` fails on a key present in only one language, duplicate keys, a Russian entry left in English, or a different set of `{params}` between the two; `hardcodedText.test.ts` parses every UI source file (TypeScript AST) and fails on JSX text, string literals in JSX children and user-facing props (`aria-label`, `placeholder`, `title`, `label`, `description`...) outside the catalogs. Technical identifiers (className, ids, data attributes, sound names, the brand "Clade") are not copy and pass.
- **Complete templates, never fragments:** a message is a whole sentence with named parameters (`"{name} is installed on this computer."`); never concatenate translated pieces (word order and endings differ). Counted nouns use plural forms selected by `Intl.PluralRules` (`{ by: "total", one, few, many, other }`; Russian needs one/few/many). Russian uses the informal "ты" for instructions, infinitives/nouns for buttons and titles, and avoids gendered wording.
- **English is the canonical fallback:** a key missing from Russian renders its English text (never crashes); a key missing everywhere renders as the key (visible in development).
- **Not translated:** Minecraft version ids, Fabric/Forge/NeoForge/Quilt, UUIDs, paths, technical log content, the brand names Clade / Clade Launcher (the window title and `nav[aria-label=Clade]` stay as they are).
- **Language setting and first run:** `ui.language` in `data/settings.json` (`en`, `ru` or absent = never chosen; anything else is repaired to absent), written only through the `set_language` command, announced by the `ui-settings-changed` event. While absent, the UI follows the Windows display language read by Rust (`system::system_locale`, `GetUserDefaultUILanguage`; reported as `systemLocale`, never stored): a locale name starting with `ru` means Russian, anything else English. **An explicit choice is never overridden automatically**, so it survives restarts, a moved folder, another drive letter or a Windows reinstall. The choice is the only control added to Settings (a two-option "Language" row, each language named in its own words); a failed save undoes the switch. Choosing switches the whole UI at once with no restart (open modals stay open and keep their focus and typed input; sounds, particles, animations and focus order are untouched).
- **Hero phrases:** each phrase has a stable id (`ready-when-you-are`, ...) and a wording per language (`phrase.<id>`), curated for tone rather than translated word for word (at most 30 characters, ending in `.` or `?`, no `!`). Only the id is remembered (`ui.last_phrase`), so switching language never corrupts it and the same phrase is simply re-worded in place.
- **Durations, sizes, dates:** the backend stores and sends raw numbers only; the UI formats them (`27h 42m` / `27 ч 42 мин`, `1.4 GB` / `1,4 ГБ`, localized month names). A short Russian month ends in a dot, which the sentence must not double.
- **Backend errors are codes, not prose:** Rust returns a stable `code` plus named `params` and never user-facing prose; its English `message` is for logs and is never shown. The shared shape is `CodedError { code, params?, message }` (`coded_error.rs`); `LaunchFailure`, `PrepareFailure`, `SignInError` carry the same `code`/`params`, and the exit summary carries a `reason` code. The frontend words them in `lib/i18n/errors.ts` (`describeError(domain, error)` / `describeCode`), with keys `error.<domain>.<code>` (domains: `launch`, `prepare`, `signIn`, `vault`, `account`, `profile`, `catalog`), then `error.common.<code>`, then the domain's `unknown`, then `error.generic`. The same code can mean different things in different domains (`offline`), hence the domains. Params are facts such as a profile name, a loader or byte counts (`requiredBytes`/`availableBytes` for `disk_space`); they never hold secrets. A new backend failure = a new code in Rust, wording in both catalogs; a test cross-checks the codes found in the Rust sources against the catalogs.
- **Native / pre-frontend dialogs (`startup_text.rs`, `startup.rs`):** anything shown before the React UI exists is localized too. The only native error dialog is `startup::fail(StartupMessage, root, detail)`; there is no raw-text entry point (a test fails if `lib.rs` or `startup.rs` calls a message box with raw text). Each situation is a `StartupMessage` id (`FolderInUse`, `FolderNotWritable`, `CannotLocateFolder`, `FolderTooNew`, `StartupFailed`, `WebViewMissing`, `WindowFailed`) with an English and a Russian text in a small native table, rendered at the final boundary; a test requires both languages for every id (different text, Cyrillic only in Russian, short, brand/product names such as Clade, Clade.exe and WebView2 untouched). A new native dialog = a new id with both texts in the same change. The dialog title is always "Clade Launcher". Technical detail is an English line after a localized label ("Details" / "Подробности"), never secrets or user paths; logs stay English.
- **Startup language resolution** is self-contained and never depends on the frontend, WebView storage or the main settings system, so a broken settings file cannot block error reporting: an explicit `ui.language` (`en`/`ru`) read straight from `data/settings.json` with a tolerant parser wins; otherwise the Windows display language (`ru...` is Russian); everything else, and any missing, unreadable, malformed or invalid settings, is English-or-Windows-language by the same rule and never fails. Order: explicit setting > Windows language > English. A unit-tested pure function (`resolve_language`) holds the rule. Development builds accept `--preview-startup-dialog=N` (1-based, compiled out of release) to show any dialog for review without damaging the folder or the WebView2 runtime.
- **Internal logs stay English** and technically useful; they are not translated and never include secrets.
- **Layout:** Russian is often wider. Fix a real overflow at the specific element (never shrink type globally, never re-balance unrelated UI). Verified in the real window at 960x600, 1280x720, 1440x900 and 1920x1080: dock, menus and modals fit, every headline stays on one line at the minimum width. Two wraps exist in English too (the account-removal buttons and "Restore default") and were left alone.
- **Verified in the real window (2026-10-04):** first run followed Windows (ru-RU) with no saved language; English -> Русский -> English switched live with Settings open and focus kept; the choice survived restarts and an explicit English beat the Russian Windows; home, settings, profile menu, Create profile (vanilla, modded, validation), account menu, account modal and removal confirmation, sign-in/passphrase dialogs, no-account and unlock dialogs, Verify files and a real (cancelled) preparation were read in both languages; a language change arriving while Create profile held typed text kept the text and focus; no console problems. Run the helper scripts in the git-ignored `shots/` (`verify-i18n-*.mjs`) the same way as the others.

## Product philosophy: vanilla-first, not a content platform (PERMANENT)
The launcher follows the spirit of the official Minecraft launcher. It is about Minecraft itself: install and launch many versions, keep several isolated local instances, and stay out of the way. It is not a mod manager and not a store.

**Never add (even if asked indirectly, even "just a small one"):**
- Any Modrinth or CurseForge integration, or any other third-party content API/host. No API keys, ever; the launcher must work with zero keys and zero accounts besides Microsoft sign-in.
- A mod browser, modpack marketplace or modpack import-from-platform, shader browser, resource-pack browser.
- Recommendations, featured content, "popular"/"new" lists, ads, news feeds, or any discovery UI.
- Mod-manager behaviour: listing/searching/updating/enabling/disabling mods, dependency resolution, reading mod metadata to present it. The instance's `mods` folder is a plain folder the user manages.
- Downloading mods, modpacks, shaders or resource packs from anywhere. If a user wants content they get it themselves and put it in an instance (copy files into the folder; an "Open instance folder" button, and at most a plain copy of local files the user picked, validated by `safe_archive`/`RelPath`, never touching the network).
- A global mods/config/saves/resourcepacks/shaderpacks folder shared by instances (see Instances).

**Allowed network (the allow-list in `download_policy.rs` is the single source of truth):** Mojang (version manifests, client jars, libraries, assets, Mojang-built Java runtimes), Microsoft/Xbox/Minecraft sign-in, and mod *loaders* from their own official hosts only (Fabric, Quilt, Forge, NeoForge; confirmed by the owner on 2026-10-04: the launcher may download and install only the loader the user selected, from that loader's official source). A loader is infrastructure needed to make a Modded instance runnable, not content; it is the only "modded" thing the launcher may fetch. The launcher prepares Minecraft and the selected loader; **all user content (mods, configs, shaders, resource packs, modpacks, worlds) is supplied manually by the user.** Java comes from Mojang's runtime manifests, not from third-party JDK vendors or code hosts.

**Enforced by tests, not just by this file:** `src-tauri/tests/product_rules.rs` fails if a content-platform or content-browser name appears in source, config or dependencies, if the allow-list differs from the approved set, or if an API-key setting appears. `download_policy` tests assert content hosts stay blocked. If a rule here must change, change this section first (with the owner's explicit decision), then update the tests, never the other way round. Do not even mention the forbidden platform names in code or comments (the scan is case-insensitive); this file and other docs are exempt.

**UI:** the home screen stays minimal and calm. No feeds, banners, promos or content rows. The total playtime is a quiet muted line under the subtitle, without new cards or sections.

## Launcher state vs. WebView state (PERMANENT)
- **Launcher-owned state is authoritative in the Rust settings service, in `data/settings.json`** (inside the portable folder): the UI sound switch and volume (`ui.sound`), the language (`ui.language`), the last headline shown (`ui.last_phrase`, a language-neutral id), and every future preference or per-user launcher state. It is sanitized on load (out-of-range or malformed values are repaired, never fatal; older files without the `ui` section load with defaults), saved atomically, and written only through `ui_settings.rs`.
- **The WebView profile (`data/webview2`) is disposable browser-engine cache.** It may be deleted or regenerated at any time and nothing launcher-owned may live only there. Therefore the frontend must never use `localStorage`, `sessionStorage`, `indexedDB`, cookies, the Cache API or WebSQL for launcher state. `src/lib/webStorageGuard.test.ts` scans the frontend source and fails if any appears.
- **Bridge:** the frontend reads once at startup (`get_ui_settings`, called in `main.tsx` before the first render, with a 1.5 s fallback to defaults so a failing backend can never block the UI), writes through `set_sound_settings` / `set_last_phrase`, and listens for the `ui-settings-changed` event (so a future second window or settings screen stays in sync; the sound service applies it with `hydrate`, which does not save again). All of it lives in `src/lib/settings/uiSettings.ts`; outside Tauri (plain-browser development, unit tests) values are kept in memory for the session and never written anywhere. A save that fails (for example a read-only stick) rolls back the in-memory value so memory never disagrees with the file.
- **Adding a new preference:** add the field to `UiPrefs`/`LauncherSettings` in `settings.rs` with a default and sanitization, expose it through `UiSettingsDto` and a command in `ui_settings.rs`, and consume it via `uiSettings.ts`. Do not introduce another persistence system.
- Verified in the real app: with the whole `data/webview2` folder deleted between launches, the sound settings and the no-repeat headline behaviour persisted across three relaunches.

## Home screen personality (headline, particles, sounds)
Subtle, calm, editorial. Never jokey, gamer-y, loud or busy; the idle hero stays still.
- **Headline** (`Hero.tsx`, copy in `features/launcher/phrases.ts`): the h1 contains a native `<button class="hero-link">` stripped of every visual trace (no background, border, pill, underline or icon), so Enter/Space/focus come for free. A fresh phrase on every start (never the one shown last launch; the id is kept in `data/settings.json` as `ui.last_phrase`, saved by the Rust settings service), and a click shows a different one (never the same twice in a row). Hover: pointer cursor, +2px lift and a slightly warmer colour over 190 ms. Focus ring: faint clay ring only for keyboard navigation (`html[data-input="keyboard"] .hero-link:focus-visible`; `lib/inputModality.ts` flips `data-input` between `keyboard` and `pointer`), never left visible after a normal mouse click; the browser's default outline is suppressed on the headline so only that ring can appear. Change animation: 170 ms fade out with a 6px upward drift, swap, 230 ms fade in from 8px below (about 400 ms total). Rapid clicks during a transition are absorbed (the phrase never queues or glitches), though press, particles and sound still respond. Reduced motion: still changes the text with a 100 ms cross-fade, no movement, no press, no particles.
- **Copy rules:** short, calm, sentence case, at most 30 characters (it must fit on one line at the 960 px minimum window), ending in `.` or `?`, no `!`, emoji, jokes, slang or motivational quotes (a unit test enforces this). Contextual messages (last instance, total playtime, time since last session) are not implemented: add a `PhraseRule` to `CONTEXT_RULES` and pass a `PhraseContext` into `Hero`; nothing else changes.
- **Particles** (`lib/fx/burst.ts`): one-shot burst of 6-12 tiny dots/strokes in palette colours from the exact click position (keyboard activation: the headline's centre), 350-650 ms, removed the instant each animation ends, with a failsafe timer, a 48-particle global cap and a layer that disappears when empty. Not a particle system; never continuous.
- **Sounds** (`lib/sound/soundService.ts`): original, procedurally synthesised with Web Audio (no audio files, no network, nothing installed or written outside the folder). Kinds: `click`, `primary` (Play), `headline`, `select`. Only on direct user action (click or keyboard activation), never on hover; the AudioContext is created lazily inside the first gesture. Quiet by design (volume 1 maps to a 0.45 gain ceiling, default 0.5), throttled (55 ms between any two, 140 ms between the same kind, at most 3 ringing). Settings architecture is ready for a later UI: `sound.setSettings({ enabled, volume })`, `sound.subscribe(...)`; every change is saved by the Rust settings service to `data/settings.json` (`ui.sound.enabled`, `ui.sound.volume`); defaults to enabled at 0.5. Do not add hover sounds, loud chimes, or externally loaded audio.
- **Verification used for these** (kept out of git in `shots/`): `verify.mjs` + `input.ps1` drive the real Tauri window with OS-level mouse/keyboard input and read live state over the WebView2 DevTools port (start the app with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9333 --remote-allow-origins=*"`; never set this in shipped code). Last run: hover/click/keyboard/rapid-click/reduced-motion all as specified, no orphan particles, no console errors.

## Instances (isolation is the core rule)
- **Creating a profile always asks two things, explicitly:** (1) *Vanilla or Modded?* and (2) *which Minecraft version?* (the user chooses it; any version Mojang publishes). In code this is `NewInstance { name, minecraft, profile }` where `profile` is `Profile::Vanilla` or `Profile::Modded { loader, loader_version }`. Both fields are required in the request (no serde default), so whatever drives creation must ask; never add a default profile type or default version. A profile's type is fixed at creation (no in-place vanilla-to-modded conversion: create a new instance).
- **Vanilla** (the default and simplest case): install only the selected Minecraft version and the Mojang runtime/files it needs. No loader of any kind, nothing mod-related. The launcher creates no `mods/`, `config/`, `resourcepacks/`, `shaderpacks/` or `saves/` for it; `game/` starts empty and Minecraft creates what it needs when it runs. Tests assert this.
- **Modded:** the user also picks one loader (Fabric, Forge, NeoForge or Quilt). The launcher may download and install only that loader, from its official source (see Loaders). `LoaderVersionSpec::Auto` lets the launcher choose the best compatible version; `Pinned` is a version the user chose from the offered list. After setup the instance is ready for the user to add their own content by hand. Modded layout, all instance-local and empty at creation: `game/mods`, `game/config`, `game/resourcepacks`, `game/shaderpacks`, `game/saves`. The launcher never puts content in them and never searches, lists, downloads, enables, disables or updates what the user puts there.
- **Setup state:** `SetupState::Pending` until the (later) install pipeline finishes, then `Ready { version_id, loader_version }` via `InstanceStore::mark_ready`. `version_id` is the launchable profile under `minecraft/versions/` (for Vanilla it must equal the Minecraft version and there is no loader version; for Modded the installed loader version is mandatory and must match a pinned one). Inconsistent manifests are refused, also on load. A `Ready` instance has everything it needs in the shared immutable stores, so it runs offline.
- **Coexistence and versions:** any mix side by side (Vanilla 1.21.x, Vanilla 1.20.x, an old release, a Fabric instance, a Forge or NeoForge instance). **Never lock the launcher to one Minecraft version**: versions are opaque ids validated only for path safety (`McVersion`, `LoaderVersion`, `VersionId` in `versions.rs`; no leading `-` or `.`); never hard-code, enumerate or special-case Minecraft versions in the launcher's own logic. (The only version-dependent knowledge is loader compatibility, taken from the loader's official catalog; see Loaders.)
- **Layout:** `instances/<id>/` containing `instance.json` (launcher-owned manifest, schema 2, `id` must equal the folder name), `game/` (the `--gameDir` and working directory: saves, mods, config, resourcepacks, shaderpacks, options, logs, crash-reports, screenshots), `natives/` (disposable), `home/` (stands in for the user profile while the game runs), `playtime.json`. The id is a lowercase slug and never changes on rename, so no stored reference can break. There is no `custom/` and no user-supplied version profile: a hand-assembled setup is simply a Modded instance whose content the user adds themselves.
- **Isolation, absolutely:** everything a player or a mod can modify lives under that instance's `game/`. Every such path comes from `InstanceDirs`, which is built from one instance directory; there is intentionally no API for a shared/global mods or config folder. Do not add one, and do not use symlinks/junctions/merging to share files between instances. A Vanilla instance must be completely unaffected by any other instance. Tests assert disjoint trees, no pre-populated vanilla dir, and that the shared layout has no `mods`/`config`/`saves`/`resourcepacks`/`shaderpacks` folder.
- **What may be shared** (root-level `minecraft/versions`, `libraries/`, `assets/`, `runtimes/`): only immutable, hash-verified files published by Mojang or the loader project. Nothing a user or mod can edit is ever stored there.
- Deleting an instance removes only its own folder (saves included, so the UI must confirm). Never run it while the instance is running.
- Instance JVM arguments and memory are user input: validated for shape, shown before launch, passed as separate arguments (never through a shell).

## Loaders (`loaders.rs`): official sources only, loaders only
- Pure module (no network or process I/O): builds official URLs, parses official catalogs, orders and picks compatible versions, and describes how a loader would be installed. The later download/launch pipeline executes the plans.
- **Official sources** (every URL is built from validated tokens and checked against `loaders::official_policy()` = `LOADER_HOSTS` only, stricter than the global allow-list; https, no ports, no redirects off the list): Fabric `meta.fabricmc.net/v2/versions/loader/<mc>` and libraries from `maven.fabricmc.net`; Quilt `meta.quiltmc.org/v3/versions/loader/<mc>` and libraries from `maven.quiltmc.org`; Forge `files.minecraftforge.net/.../promotions_slim.json` and installers from `maven.minecraftforge.net`; NeoForge `maven.neoforged.net/api/maven/versions/releases/net/neoforged/neoforge` and installers from the same Maven. Never any other host, mirror or third-party "loader download" site.
- **Compatible versions:** `parse_catalog` returns versions compatible with the chosen Minecraft version, newest first, labelled by `Channel` (Recommended, Stable, Latest, Prerelease); an empty list means "no compatible loader" (the UI says so; never guess). `choose_auto` picks recommended, then stable, then latest, then prerelease. Fabric/Quilt catalogs are filtered by the server per Minecraft version; Forge uses its `recommended`/`latest` promotions; NeoForge versions are mapped by convention (Minecraft 1.A.B -> `A.B.x`, 1.21 -> `21.0.x`), with no match for 1.20.1 and earlier, snapshots, or unknown future schemes. Catalog bodies are bounded (8 MiB), parsed strictly, and every version string is validated.
- **Install plans (`install_plan`):** Fabric/Quilt: a version-profile JSON plus its libraries, each verified with the sha1/sha256 and size inside the profile; no code is executed. Forge/NeoForge: the official installer jar, which must be verified against the `.sha256` published beside it on the same Maven and only then run with the launcher-managed Java in a scratch directory under `cache/` (never as admin, never from a path outside the folder), after which the resulting libraries and profile are moved into the shared stores. Residual trust to state honestly: that checksum comes from the same host as the jar (it catches corruption/tampering, not a compromised loader project), and the installer's own library downloads are made by that official program, not by our allow-listed downloader. Older Forge releases (before roughly 1.12) may use a different installer file name; verify against the Maven before enabling them.
- Loader output (profile JSON, libraries) is immutable and goes in the shared stores; the loader is never installed into an instance's `game/` folder.

### Loader installation is sandboxed inside the portable root (`loader_install.rs`)
Hard rule: Fabric, Forge, NeoForge and Quilt installation must never use the global `.minecraft`, user-profile caches, the system TEMP directory, or any machine-specific path, and must never need administrator rights. Every loader-generated file, library, temp file and metadata stays under the launcher root.
- **Why it is necessary (read from the official Forge installer source):** with no usable target it defaults to `%APPDATA%\.minecraft` on Windows (the variable comes from the process environment) and to `user.home`/`.minecraft` elsewhere, and it requires a `launcher_profiles.json` in its target. It also has its own trusted-host list and a `--mirror` option; we never pass `--mirror`.
- **Staging:** every installation gets a fresh `StageSession` under `cache/loader-install/<id>/` with `mc/` (the installer's explicit target, containing a stub `launcher_profiles.json`, plus the vanilla version seeded from the shared store), `home/` (stands in for the user profile, with `AppData/Roaming` and `AppData/Local`) and `tmp/` (stands in for system TEMP). Stale stages from a crash are swept at every start.
- **Scrubbed process:** `InstallerCommand::to_process` clears the environment completely and sets only: the read-only Windows system directory (`SystemRoot`, `windir`, `PATH` = its `System32`) and `TEMP`/`TMP`/`TMPDIR`/`USERPROFILE`/`HOME`/`APPDATA`/`LOCALAPPDATA` pointing into the stage, plus `-Djava.io.tmpdir` and `-Duser.home` (Java derives `user.home` from a Windows API, not the environment, so the JVM flag is essential). Nothing inherited from the user's session reaches the installer (a unit test runs a real child process to prove it). `JAVA_HOME`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`, `CLASSPATH` are refused. Java is always the launcher-managed runtime.
- **Redirect where possible, fail closed otherwise:** because the machine-specific locations are redirected, a mis-passed or ignored target argument can only land inside the stage. `verify_command` additionally refuses (and the spawner must call it again right before spawning) any program, working directory, argument or environment value that is an absolute path outside the launcher root, contains `..`, is `--mirror`, or is missing a required redirection.
- **Tripwire:** `Tripwire::arm(Tripwire::global_minecraft_dirs())` before the run and `check()` after it detects any change to the real `%APPDATA%\.minecraft` or `~\.minecraft` and fails the installation loudly (it cannot undo a write; it makes a leak impossible to miss). It only observes those paths and never uses them.
- **Merging results:** `merge_stage_into_shared` takes only `libraries/` and `versions/` from the stage into `libraries/` and `minecraft/versions/`; everything else (logs, caches, the stub profile) is discarded with the stage. All paths are validated as `RelPath`/`VersionId`, links are refused, an existing file is never overwritten with different content (checked by SHA-256, all-or-nothing), and re-merging identical content is a no-op.
- **Fabric/Quilt:** no installer process at all (`NoInstallerNeeded`). The (untrusted) profile JSON's library coordinates go through `library_relpath`, which only accepts `group:artifact:version[:classifier][@ext]` made of safe tokens and always yields a path under `libraries/` in the standard Maven layout.
- **Verified with the real installers (2026-10-04):** `--installClient <dir>` works with the current Forge (54.1.14) and NeoForge (21.4.158) installers run through this sandbox; the flags live in `client_install_flags`. The sandbox's safety never depended on them.
- **Residual limits:** the JVM may still write Java preferences to the Windows registry (not redirectable); the installer makes its own network requests (the Forge installer restricts itself to its trusted hosts; ours cannot restrict a third-party program's network access); the tripwire detects but cannot reverse a leak; an installer that spawns detached grandchildren is out of reach.

### Guard tests (do not weaken; extend deliberately)
`src-tauri/tests/portability_rules.rs` scans all production Rust code (stops at the first `#[cfg(test)]`, ignores comments) and fails on: ambient environment lookups (`env::var*`, `set_var`, `remove_var`, `env::current_dir`), the system TEMP (`env::temp_dir`, `tempfile::tempdir()`, `NamedTempFile::new`, `tempfile::tempfile`), Tauri AppData paths (`app_data_dir`, `app_config_dir`, `app_cache_dir`, `app_local_data_dir`, `app_log_dir`), `dirs::`/`directories::`, bare process spawning (`Command::new`), `.minecraft` path literals, and hard-coded absolute Windows path literals. A genuine exception needs a `portability-allow: <reason>` comment on or within three lines above the line, and the exact set of exceptions is pinned in the test (currently: the Windows system-directory lookup and fallback, the single scrubbed spawn site, and the read-only tripwire in `loader_install.rs`; the WebView2 runtime variable in `webview.rs`). A self-test proves the scanner detects each construct. New code that must spawn a process (the future game launch) should go through the same scrubbed-environment approach and add its exception here consciously.

## Profile creation and the official version catalog (`profiles.rs`, `mc_catalog.rs`, `loader_options.rs`, `net.rs`)
- **Ownership:** the frontend never fetches Minecraft or loader metadata. Network policy, caching, validation and filesystem access live in Rust; the UI only calls the commands `list_profiles`, `select_profile`, `get_version_catalog`, `get_loader_options`, `create_profile` (`src/lib/profiles/api.ts` validates the replies, invents nothing, and rejects outside Tauri; there are no fake profiles in production code).
- **Network layer (`net.rs`):** `Fetcher` trait; `HttpFetcher` is https-only, re-checks every redirect host against the policy, caps response size, uses 6 s connect / 15 s total timeouts and an anonymous `Clade/<ver>` User-Agent. Tests inject `FakeFetcher`. Version metadata uses the global allow-list; loaders use the stricter `loaders::official_policy()`.
- **Minecraft catalog:** only Mojang's `piston-meta.mojang.com/mc/game/version_manifest_v2.json`. All four kinds are kept (release, snapshot, old_beta, old_alpha; the UI's "Historical" = old beta + old alpha). Releases are the default view, never the only one. Ids may contain a single interior space (real Mojang ids such as `1.14.2 Pre-Release 4`), but never a leading `-`/`.` or anything that fails `RelPath`.
- **Cache (`cache/catalogs/`, inside the portable root, no absolute paths, atomic writes):** `version_manifest.json` is fresh for 1 h; after that a refresh is attempted, and on network failure the last valid copy is used and flagged `CacheStale` (origin is `Network` / `CacheFresh` / `CacheStale`; the UI shows a quiet note for stale data). A response is saved only after it parses and passes a plausibility gate (at least 90% of the cached entry count), so a malformed or truncated response can never destroy a valid cache.
- **Loader cache:** Forge and NeoForge publish one catalog for all Minecraft versions, so the RAW catalog is cached (`loader-forge.json`, `loader-neoforge.json`) and filtered for the requested version on every read. Fabric/Quilt answer per version, so their offers are cached per version (`loader-fabric--<mc>.json`, pruned to the newest 24). **Never cache an already-filtered result under a name shared by several Minecraft versions** (a real bug: offline, Forge 1.20.1 showed 1.21.4's loader). Offline and never-seen means `Unavailable`, not a guess. NeoForge maps `1.A.B` to `A.B.x` from 1.20.2, and the new `26.x` scheme to a zero-padded series; anything else is "none".
- **Creation is verified server-side (`create_verified`):** the UI is not trusted. It checks the name (duplicate names refused; ids are race-free slugs from `InstanceStore`), that the Minecraft version is in the catalog, that the loader has a compatible version, and that a pinned loader version was actually offered; it never guesses. Then it creates a `Pending` instance (no download or install happens yet) and stores it as `last_instance` in `data/settings.json`, which is how the selection survives restarts.
- **UI:** the dock shows `Name · Vanilla 1.21.4` / `Name · Fabric 1.20.1`; the menu lists profiles and ends with "+ Create profile". Vanilla never asks about loaders; Modded reveals Loader and Loader version (recommended by default; incompatible loaders are disabled with a reason). The hero shows `Played <total>` from the real backend total, muted, hidden at zero.
- **Verification method:** `shots/` (git-ignored) drives the real window with OS input; offline is simulated with `HTTPS_PROXY=http://127.0.0.1:9` plus an aged cache. Last run: all four loaders, filters, keyboard, offline, restart persistence and a file watcher showed no writes outside the folder.

## Accounts, settings and modals (PERMANENT product rules)
### Accounts are independent from instances
- **Hard rule:** an account is never bound to an instance. Instances/profiles define the Minecraft version, Vanilla or Modded, the loader and the instance's files; accounts define the Microsoft/Minecraft identity (Java profile name and UUID, skin, owned capes). The selected account can launch any compatible local instance, so the same "Vanilla 1.21.4" runs with Account A or Account B with no duplication. Neither `instance.json`, any instance file, nor playtime ever references an account, and selecting or removing an account changes none of them (tests assert this).
- **Only the selected account is persisted globally**, as a convenience (`accounts.json` `active`, repaired to the first account when missing or dangling). It is session state, not part of an instance manifest.
- **Code:** `accounts.rs` (metadata file, no tokens), `accounts_api.rs` (DTOs, `list_accounts`, `select_account`, `remove_account`, the `Capabilities` flag set that tells the UI what this build can do), `auth.rs` + `ms_auth.rs` (sign-in, see below), `src/lib/accounts/api.ts` (validating bridge; invents nothing outside Tauri; only inline `data:image/png` heads are ever drawn). `remove_account` also deletes the account's vault secrets.
- **No mock accounts in production code.** Fixtures exist only in tests (`LauncherAccounts.test.tsx`) or hand-written dev files under `clade-root`.
- **Dock:** the account control opens a compact menu: head + Java profile name per account, the active one checked, a manage (gear) item that appears on row hover or keyboard focus, then "+ Add account". With no accounts it reads "Sign in" and offers only "+ Add account". Never a large dashboard.
- **Sign-in is implemented** (next section) up to Mojang's approval step. Tokens only in the encrypted vault; Microsoft may ask to sign in again on another PC and that is fine. Never a custom Microsoft password form.

### Microsoft / Xbox / Minecraft Java sign-in (`ms_auth.rs`, `auth.rs`)
Researched and verified 2026-10-04 against Microsoft's identity-platform docs and the community Minecraft Wiki (Mojang publishes no formal spec for the Minecraft-side steps). Implemented and tested **up to Mojang's approval step**; see "Open owner action" below.
- **Registration (owner-created, done):** Entra app, personal Microsoft accounts only (`consumers` tenant, required for `XboxLive.signin`), public client (no secret, "Allow public client flows" on), redirect URI `http://localhost`. The public client id `27200331-f467-4c61-a013-b307305c4ccf` is a constant in `ms_auth.rs` (not a secret). Verified live: Microsoft's authorize endpoint serves the sign-in page for this client id with a `http://localhost:<port>` redirect and rejects a foreign redirect; the token endpoint answers a garbage code with `invalid_grant` (not `invalid_client`). Never use another launcher's client id; never ship a secret.
- **Flow:** OAuth 2.0 authorization code + PKCE (S256, 32-byte verifier) in the **system browser** (opened with the opener plugin; the launcher never shows a login form and never sees a password), random 32-byte `state`, `prompt=select_account` (so several Microsoft accounts can be added), scope `XboxLive.signin offline_access`, against `login.microsoftonline.com/consumers/oauth2/v2.0/{authorize,token}`. Then `user.auth.xboxlive.com/user/authenticate` (`RpsTicket d=<token>`), `xsts.auth.xboxlive.com/xsts/authorize` (relying party `rp://api.minecraftservices.com/`), `POST api.minecraftservices.com/authentication/login_with_xbox`, `GET /minecraft/profile` (the account is launch-ready only when this returns a valid name and UUID). A 404 there is "no Java profile"; `GET /entitlements/mcstore` only decides which message to show (owns the game but no profile yet, versus does not own Java Edition).
- **Redirect listener (`Loopback`):** `127.0.0.1`, random port, redirect URI `http://localhost:<port>`; one connection at a time, 3 s read cap, 8 KiB head cap, 5 min overall wait. A request counts only if it is `GET /`, its `Host` is this listener (DNS-rebinding guard) and `state` matches in constant time; anything else gets a 404 and is ignored. `error=access_denied` means cancelled. The reply page echoes nothing. Cancelling (button, Escape, or closing the browser flow) stops the listener and the in-flight requests; after any outcome the launcher window is brought back to the front.
- **Transport:** `net::Transport` (POST with headers; redirects never followed; same https-only allow-list; `HttpRequest` `Debug` is redacted). Tests use `FakeTransport`. `ms_auth::ENDPOINTS` is asserted against the allow-list.
- **Secrets:** `Secret` (zeroized, redacted `Debug`) everywhere; error values and logs carry codes (`AuthError::code()`), never bodies, tokens or headers (the only sign-in log lines are `signed in a Minecraft Java account` and `sign-in did not complete code=...`). Refresh token, Minecraft access token and its expiry go to `data/vault.bin` only (`AccountSecrets`). **`accounts.json` holds metadata only**: internal id, Minecraft UUID, Java profile name, status, timestamps (tests assert no token-like field or value). Verified in the real app: no passphrase, token, Bearer or JWT text in `vault.bin`, `accounts.json`, `settings.json` or logs; no writes outside the folder (watcher and registry diff: nothing launcher-related; the default browser's own files are the browser's).
- **Vault UX:** the vault needs a master passphrase (Argon2id; there is no machine-bound shortcut, by design). First sign-in asks to create one (8+ characters, repeated, "can't be recovered"); later sessions ask to unlock when a sign-in or refresh is needed. The vault must be unlocked **before** the browser opens so a finished sign-in can always be saved. The passphrase is sent to Rust once and never kept in the frontend (fields are cleared on every attempt); the unlocked vault lives in memory until the app exits. Removing an account while the vault is locked leaves its encrypted entry, which is purged at the next unlock.
- **Accounts list rules:** the same Minecraft UUID never creates a second entry (it updates the existing one, including a renamed profile); the newest sign-in becomes the active account (still global convenience state, never part of an instance); "Sign in again" (account modal, or a failed refresh) must come back as the same UUID or it is refused (`wrong_account`). Order of writes: vault first, then metadata, so a crash leaves at most an orphaned secret.
- **Token lifecycle (`ensure_fresh`):** returns the cached Minecraft token while it has more than 5 minutes left; otherwise refreshes the Microsoft token and repeats the chain, and stores the **rotated** refresh token. `invalid_grant`, `interaction_required`, `consent_required`, `login_required` (and a missing secret) mark the account **needs sign in again** and keep it and its data; 5xx/429/network failures change nothing (`offline`). The launch core must call `ensure_fresh` right before launching (`refresh_account` is the command for it). Accounts are never deleted because credentials expired.
- **Errors the UI tells apart (`AuthError::code()`):** `cancelled` (silent close), `timed_out`, `browser_unavailable`, `offline`, `oauth`, `needs_sign_in`, `no_xbox_account`, `xbox_region`, `adult_verification`, `child_account`, `xbox_banned` (XSTS 2148916233/35/36/37/38/27), `xsts`, `approval_required`, `no_java_profile`, `bad_response`, `vault_locked`, `storage`, `wrong_account`. Microsoft sign-in working while Minecraft Java is unavailable is `no_java_profile`, never a generic failure.
- **UI:** `SignInDialog` (the same `Modal`): passphrase create/unlock if needed, then `Opening Microsoft sign-in…` / `Waiting for sign-in…` / `Finishing setup…` (events `sign-in-progress`), Cancel, plain errors with Try again. No large login screen.
- **Open owner action (as of 2026-10-04): Mojang has not yet approved the client id.** Without that approval `login_with_xbox` answers 403 "Invalid app registration" and the launcher shows "Microsoft sign-in worked, but Mojang has not approved this launcher for Minecraft sign-in yet" and saves nothing. This is by design: do not bypass it. The form is linked from https://aka.ms/mce-reviewappid (also https://aka.ms/AppRegInfo); Microsoft Q&A reports the individual-developer route is unclear. Everything after `login_with_xbox` (entitlements, profile, persistence, refresh) has only been exercised against a scripted transport, never a real Minecraft account; re-verify with a real account once approved.
- **Known limits:** a complete real sign-in needs a person to type their own credentials into Microsoft's page, so it is not automated; the launcher opens the user's default browser, which keeps its own history and cookies outside our control; the redirect listener is plain HTTP on loopback (standard for native apps, RFC 8252); if loopback is blocked the documented fallback is the device-code flow (not built). Live check: `cargo test -- --ignored live_` talks to Microsoft with invalid values only.

## Preparing a profile (the installation core)
`prepare.rs` turns a Pending profile into a Ready one: everything a launch will need is installed and verified. It does **not** start the game. Modules: `download.rs` (pipeline), `mc_meta.rs` (what Mojang's metadata requires), `java_install.rs` (Mojang's Java runtimes), `natives.rs`, `loader_prepare.rs` (Fabric/Quilt/Forge/NeoForge), `prepare.rs` (orchestration, progress, offline check), `prepare_cmd.rs` (Tauri commands `prepare_profile`, `cancel_prepare`, `prepare_status`, event `prepare-progress`).
- **Lifecycle:** manifest `Pending` -> (runtime only: Preparing) -> `Ready { version_id, loader_version }`. `Preparing` and `Failed` are runtime states in `PrepareState` (the manifest never says Ready until the last check passed, so a crash cannot leave a half-prepared Ready profile). A failure keeps a structured error (`PrepareFailure { code, message }`; codes: `cancelled`, `offline`, `network`, `verification`, `metadata`, `unsupported`, `java`, `loader`, `storage`, `not_found`, `busy`) until the next attempt. One preparation runs at a time.
- **Order:** read the version JSON (found through the official catalog entry's `url` + `sha1`, verified, saved to `minecraft/versions/<id>/<id>.json`; an already-saved valid copy needs no network) -> asset index -> Java plan -> loader plan (Fabric/Quilt profile) -> **totals are planned before big downloads start** -> Java -> client jar + logging config -> libraries -> assets -> natives -> loader -> final file check -> `mark_ready`. Modded profiles always prepare their Vanilla version first.
- **Where things go (all relative to the Clade folder; nothing absolute is persisted):** shared and immutable: `minecraft/versions/<id>/{<id>.json,<id>.jar}` (Vanilla and loader profiles side by side), `libraries/<maven path>`, `assets/{indexes,objects/xx/<sha1>,log_configs,virtual/<name>}`, `runtimes/java/<component>--<version>--windows-x64/`. Per instance only: `instances/<id>/natives/` (rebuilt every time) and, for the pre-1.6 asset layout only, `instances/<id>/game/resources/`. Scratch: `cache/tmp` (swept at startup), `cache/java-staging`, `cache/loader-install` (swept at startup), `downloads/` (verified installer jars). Verified: no file outside the folder, no registry change, the user's real `.minecraft` untouched.
- **Metadata rules (`mc_meta.rs`):** only Mojang's data decides what is needed. Libraries follow Mojang `rules` for Windows x64 (`os.name`, `os.arch` x64/amd64 only, literal-prefix `os.version`, all launcher `features` off; anything not understood counts as "does not match", never guessed). Library forms: `downloads.artifact`; the historical `natives` map + `downloads.classifiers` (`${arch}` -> 64; jar only extracted, not on the classpath); the modern separate `...:natives-windows` libraries (on the classpath and also extracted); loader libraries that carry only a Maven name + base url + hashes (a `.sha1` published beside the file is used only when no hash exists); `url: ""` entries that an installer generates (must exist, cannot be downloaded). Asset layouts: hash objects; `virtual` (copied to `assets/virtual/<name>`); `map_to_resources` (copied into the instance). No `javaVersion` means `jre-legacy`. Every path is a validated `RelPath`, every hash shape-checked, unknown fields ignored.
- **Downloads (`download.rs`):** HTTPS only through the existing allow-list (large files use a streaming client with a 6 s connect timeout and a 30 s read timeout but no total limit; loader jars use the stricter loader-hosts policy). Each job has a mandatory SHA-1/SHA-256 and usually a size. Existing verified files are reused (no network); bytes stream into `<file>.part` and resume with `Range` (a server that ignores it restarts the file; a part is never trusted until it verifies in full); finalisation is an atomic rename; 3 transient retries (0.4 s, tripling) and 2 corrupt-result retries; `404` and friends fail at once; a good file is never replaced by an unverified one; cancellation is checked between chunks and keeps the part; concurrency is bounded by the setting `max_concurrent_downloads` (default 8, 1-16).
- **Java (`java_install.rs`):** Mojang's runtime index (`.../v1/products/java-runtime/<hash>/all.json`, platform `windows-x64`) -> component manifest (checked against the SHA-1 in the index) -> every file downloaded raw and verified into `cache/java-staging/<id>/`, `runtime.json` written last, then the folder is renamed into `runtimes/java/` in one step. A runtime is reused while `bin/java.exe` still matches the recorded SHA-256 (`resolve_java`); no `JAVA_HOME`, `PATH`, registry or vendor JDK is ever consulted. `java_exe` is `bin/java.exe`; `javaw.exe` sits beside it (the launch stage can pick it). Components seen live: `jre-legacy` (8), `java-runtime-gamma/beta` (17), `-delta` (21), `-epsilon` (25).
- **Natives (`natives.rs`):** each native jar is unpacked by `safe_archive` (traversal, absolute/drive paths, links, case collisions, size/entry/ratio limits) into scratch, `META-INF`, `*.sha1`, `*.git` and the library's own `extract.exclude` are dropped, and the result replaces `instances/<id>/natives/` in one rename.
- **Loaders (`loader_prepare.rs`):** the version is the pinned one or the best from the loader's official catalog (Auto; works offline from the saved catalog). Fabric/Quilt: the official profile JSON (must name this Minecraft version in `inheritsFrom`) is saved and its libraries verified. Forge/NeoForge: the official installer jar is verified against the `.sha256` published beside it **before** it is ever run, then runs only inside `loader_install`'s sandbox (scrubbed env, redirected home/AppData/TEMP, tripwire on the real `.minecraft`, `verify_command` twice, 20 min limit, cancellable); the launchable id is read from the single version folder the installer produced; only `libraries/` and `versions/` are merged; then every library the produced profile names is verified (generated ones must exist). `InstallerRunner` is the seam tests use; the real one (`ProcessRunner`) goes through `InstallerCommand::to_process`, the single allowed spawn site. Residual trust: the installers do their own library downloads (their trusted hosts, their own checks), which we cannot restrict.
- **Offline:** `check_installed`/`check_files` look only at local files (existence and exact size; no hashing, no network) for the version JSON, client jar, every library, logging config, asset index and every asset object, natives, the Java runtime and the loader profile and its libraries. A Ready profile that passes is "prepared" instantly with the network gone; one that fails is repaired (online) or reports `offline` naming what is missing. Only a missing/truncated file is detected offline: same-size corruption needs `Ctx::verify_all` (re-hashes everything; not wired into the UI yet).
- **Progress (`PrepareProgress`):** stages `planning, java, minecraft, libraries, assets, natives, loader, verifying, done` with labels ("Preparing Minecraft", "Preparing Java", "Downloading libraries", "Downloading assets", "Extracting natives", "Installing Fabric", "Verifying files", "Ready to play."), `itemsDone/itemsTotal`, `bytesDone/bytesTotal` of the whole preparation and `overall` 0-1. These are `null` unless the total is known: nothing is measured while planning, extracting natives, or **while a Forge/NeoForge installer runs** (the UI shows an indeterminate bar). A ticker emits every 150 ms. Reused files count as done at once.
- **UI:** the primary dock button reads "Set up" for a profile that is not prepared and "Play" once it is (with no profile it starts creating one). Clicking either opens `PrepareDialog` (the shared `Modal`): stage label, "412 of 640 files", "184 MB of 521 MB", a real progress bar or an indeterminate sweep, Cancel (also Escape; keeps the downloaded files). It ends with "Ready to play." and "<name> is installed on this computer." There is no downloads dashboard, and it never pretends the game started. The dialog starts the preparation exactly once even when React re-runs effects in development.
- **Verified live (2026-10-04, real Mojang/loader servers, `shots/verify-prepare*.mjs`):** Vanilla 1.21.4 (182 s cold: Java 21, ~512 MB assets), the latest snapshot 26.4-snapshot-2 (86 s, Java 25), b1.7.3 (45 s, legacy Java 8, pre-1.6 assets), Fabric, Quilt, Forge 54.1.14 and NeoForge 21.4.158 on 1.21.4 (6-59 s on top of the shared stores; the real installers ran in the sandbox) all became Ready. A hard kill during libraries/assets left 8 `.part` files and 6047 verified files; after restart it finished in 109 s and rewrote none of the already verified files. Truncated library, deleted asset and truncated asset were all repaired. Offline (a dead proxy) every Ready profile was confirmed in about a second; a profile whose files are damaged or never prepared fails with a plain "Can't reach the network" message. The whole folder (executable + data) copied to another path with spaces, with no network, kept all seven profiles Ready (0.3 s each); no text file anywhere stores an absolute path. Not tested: a different drive letter (only C: exists here).
- **Limits and notes:** disk space is not checked before downloading; the first Forge/NeoForge run downloads the installer's libraries into a throwaway stage before merging; `Ready` is only as good as the offline check above; Windows may need `cargo clean -p <crate>` when App Control blocks a fresh build script (see Commands).

## Launching (the process core)
`launch_args.rs` builds the command, `launch_cmd.rs` is the pre-launch pipeline and the Tauri side, `game_session.rs` supervises the running game, `system.rs` reads RAM and free disk space. Commands: `launch_profile`, `launch_status`, `open_game_logs` (and `prepare_profile` with `verify`); event `launch-state` (`launching`, `playing`, `stopped` + exit summary).
- **Pre-launch (`plan_launch`, never starts anything, fully unit-tested):** the profile must be Ready -> a selected, launch-ready account (`no_account`; `needs_sign_in` + the account id) -> the lightweight integrity check (`prepare::check_installed`: existence and exact sizes only, no re-hashing of thousands of assets) -> `needs_repair` -> the profile's own verified Java (`find_installed`/`resolve_java`, never `PATH`/`JAVA_HOME`/registry; a swapped `java.exe` or a missing runtime is `needs_repair`, never a fallback) -> fresh credentials through the existing hook `auth::ensure_fresh` (`vault_locked`, `needs_sign_in`, `offline` when a needed refresh cannot happen, `approval_pending` when Mojang's approval is the blocker). **There is no offline, guest or "cracked" mode and none must be added**: an expired token that cannot be refreshed stops the launch. The account is global session state: switching it changes only the identity arguments; the instance manifest, files and playtime are untouched (tested byte for byte).
- **Command construction (`launch_args`):** the version chain (`inheritsFrom`) is resolved from the saved metadata: loader libraries first, duplicates (`group:artifact[:classifier]`) keep the loader's copy, JVM and game arguments are the base's then the loader's, main class is the loader's, `${version_name}` is the base Minecraft version and its jar closes the classpath (this is what Forge/NeoForge's `-DignoreList=...${version_name}.jar` expects). Modern `arguments.jvm/game` use Mojang rules (Windows x64, every launcher feature off); older versions use `minecraftArguments` plus the default JVM arguments the official launcher always added (`-Djava.library.path`, `-Dminecraft.launcher.brand=Clade`, `-Dminecraft.launcher.version`, `-cp`); the oldest use positional arguments and `${auth_session}` (`token:<token>:<uuid>`). Placeholders: auth name/uuid (undashed)/token/session, `user_type=msa`, `user_properties={}`, empty `clientid`/`auth_xuid` (the game accepts them empty), version name/type, game dir, assets root, `game_assets` (hashed: assets root; 1.6-1.7 `virtual`: `assets/virtual/<name>`; pre-1.6: the instance's `game/resources`), asset index, natives dir, classpath, `classpath_separator` `;`, `library_directory`, logging `${path}`. An unknown placeholder becomes empty. A command over 30,000 characters is refused (Windows limit).
- **JVM defaults:** only `-Xmx` plus `-XX:+UseG1GC` on Java 8, the process temp (`-Djava.io.tmpdir`), `-Duser.home`, the metadata's own arguments, the logging argument, then the profile's own `extra_jvm_args` (validated when saved). Memory: a quarter of the RAM, at least 2 GiB, at most 8 GiB, never more than half the machine, in 256 MiB steps (unknown RAM: 2 GiB); the profile's `memory_mb` overrides it within 512 MiB and three quarters of the RAM. The future per-profile override surface is exactly those two existing manifest fields; there is no JVM settings UI.
- **Isolation:** the process runs with `cwd` and `--gameDir` = `instances/<id>/game/`; its environment is cleared and rebuilt: `SystemRoot`/`windir`/`PATH` (System32) plus `TEMP`/`TMP` = `cache/game-tmp/<id>` (removed when the game ends) and `USERPROFILE`/`HOME`/`APPDATA`/`LOCALAPPDATA` = `instances/<id>/home/` (also `-Duser.home`), so nothing a game or mod writes by default lands on the machine. No `JAVA_HOME`, `CLASSPATH`, `JAVA_TOOL_OPTIONS`... (`GameCommand::to_process` is the single allowed spawn site for the game; `tests/portability_rules.rs` pins it). The game is started directly (no shell) with the verified `bin/java.exe` and `CREATE_NO_WINDOW`.
- **Secrets:** the token lives in a `Secret` and in the argument vector only. `GameCommand`'s `Debug` and `redacted()` (replaces secrets, hides the value after `--accessToken`/`--session`, shows the Clade folder as `<clade>`) are what get logged; `Identity`'s `Debug` is redacted; every session-log line also passes a `Redactor` built from the session's secrets. Verified in the real app: no token or passphrase in any log, manifest or data file.
- **Lifecycle (`game_session::supervise`, `launch_cmd`):** `LaunchState` reserves the profile at the first Play click (duplicate clicks and a second launch of the same profile are refused: `already_running`; other profiles are independent). After a successful spawn the playtime session begins (`begin_session`, only now), a 60 s heartbeat ticks it, and when the process exits it is banked: a crash, a non-zero exit or a kill still counts the time actually played, idle Clade time never does. The UI button goes Play -> "Launching…" -> "Playing" (after the process has been alive for 2.5 s; a process that dies sooner is "failed to start") -> Play, "Repairing…" while the preparation dialog repairs the profile, and it is disabled while busy. The supervisor is an independent task: it does not depend on the window.
- **Closing Clade while a game runs:** `on_window_event` hides the window instead of closing it (no tray icon, no service, nothing installed) and sets `exit_when_idle`; the game and its playtime tracking continue; when the game ends Clade exits by itself. Starting Clade again while it is hidden wakes that window (`startup::wake_running_instance`, run when the folder lock is found held, before any recovery or cleanup could touch the running session; a lock held with no window on this PC is still reported as "in use, possibly on another PC") and cancels the pending exit (window focus). If Clade itself is killed during a game, the game keeps running and the next start banks the journalled playtime (up to the last 60 s heartbeat); a game left running by a dead Clade cannot be re-attached.
- **Logs and errors:** per-session logs `logs/games/<instance>/<unix>.log` (redacted command header, all stdout/stderr, footer with the exit code and duration; 24 MiB cap, newest 10 kept). The exit is classified from the last 250 lines into one short sentence (`ExitKind` normal / crashed / failed_to_start; patterns: wrong Java version, missing main class or files, out of memory or cannot reserve heap, native library failure, access violation / `hs_err`, mod loader or Mixin errors, missing class). The backend sends the reason as a stable code (`ExitSummary.reason`: `wrong_java`, `out_of_memory`, `native_library`, ...); the UI words it in the selected language (title "Minecraft stopped") with "Open logs" (`open_game_logs`). The English sentence stays in the session log only. No crash-report dashboard.
- **Integrity and repair:** a refused launch (`needs_repair`) opens the normal preparation dialog, which repairs through the existing pipeline. "Verify files" in the profile menu runs `prepare_profile(verify: true)`: every file is re-hashed (labels read "Verifying ..."), which finds same-size corruption the quick check cannot see. Libraries whose metadata has neither a size nor a hash (all of Quilt's, Fabric's own jars) are verified once through the `.sha1` beside them and their size is recorded in `<version>.sizes.json`, so truncation is noticed offline later (profiles prepared before this existed get the record on their next repair or verification).
- **Disk space (`prepare.rs`, `system.rs`):** after planning and before anything big downloads, the bytes still to download (planned files that are absent or the wrong size, plus the Java runtime if it must be installed) get headroom (+10%, +384 MiB, +768 MiB when a loader installer will run) and are compared with the free space on the Clade drive (`GetDiskFreeSpaceExW`, no AppData); too little fails early with `disk_space` and a plain message; nothing to download means no check.
- **Verified for real (2026-10-04):** all eight prepared dev profiles (Vanilla 1.21.4, snapshot 26.4-snapshot-2 on Java 25, b1.7.3 on Java 8, Fabric, Quilt, Forge, NeoForge, 1.19.4 on Java 17) were started by the real JVM from the constructed command and reached Minecraft's own startup (`cargo test live_real -- --ignored --nocapture`, with an obviously fake placeholder identity used only for this wiring check). In the real window, with **development fixture accounts** (placeholder tokens written by `cargo test seed_dev_fixture -- --ignored`; not a Microsoft login): unlock -> Launching -> Playing; the process is the managed Java with the instance's game dir/home; closing Clade keeps Clade and the game alive (window hidden) and Clade quits when the game does; a crash shows the dialog; a normal close shows nothing; killing Clade mid-game and restarting banked the journalled 60 s; a truncated library, a corrupted `java.exe` and a missing Java runtime were each refused and repaired through the preparation dialog (Fabric then launched); no account, an account needing sign-in and a locked vault each gave their own dialog; a moved copy of the whole folder with no network launched Vanilla and Forge; the real `.minecraft` was untouched; no registry or file writes outside the folder (file watcher + registry diff).
- **PENDING:** the final launch with a **real authenticated Minecraft account**. It needs a real Microsoft sign-in, which needs Mojang's approval of the client id (see the sign-in section). Until then the launch pipeline is complete and tested up to the point where real credentials are required, and nothing fakes success: with no real account the Play button leads to "Add an account".

## Playtime tracking
- Counts only the lifetime of a launched game process. Launcher idle time, downloads and browsing never count.
- Stored inside the portable folder: `instances/<id>/playtime.json` (per instance; travels with a copied instance and is removed with it), `data/playtime.json` (lifetime across all instances; survives deleting instances), and the crash journal `data/playtime-active/<session>.json`.
- Durations use a monotonic clock, never wall-clock differences (changing the system clock cannot change playtime). The tracker is ticked every 60 s; a tick that arrives after more than 180 s (PC slept, launcher frozen) counts one interval, not the gap.
- Crash recovery: `PlaytimeStore::recover` runs at every launcher start (already wired in `run()`), banks any session left in the journal up to its last heartbeat (at most ~60 s lost), and sets unreadable entries aside as `.corrupt`. Banking is idempotent per session id, so a crash between the two file updates cannot double count.
- Closing the launcher window while the game runs does not stop tracking: Clade stays alive (hidden) until the game exits (see Launching). Only a killed Clade loses up to one heartbeat.
- Playtime files hold only numbers, ids and timestamps: no paths, no secrets.
- Wired in `launch_cmd`/`game_session`: `begin_session` right after the spawn succeeds, `tick` every 60 s, `finish` when the process exits. The home screen shows the real total.

## Architecture
- `src-tauri/src/`: Rust owns all privileged work: auth, downloads, file system, Java runtimes, process spawning, updates.
  Implemented foundations: `instances` (Vanilla/Modded profile model and isolated store), `loaders` (official loader catalogs, version selection, install plans; pure), `loader_install` (sandboxed loader installation: staging, scrubbed installer process, tripwire, merge into shared stores), `versions` (validated version ids), `playtime` (session tracking + crash recovery), `portable/` (root discovery, `RelPath`, atomic IO, hashing, folder lock), `vault` (encrypted credentials), `accounts` (metadata only), `settings`, `accounts_api` (account list and selection), `profile_service` (skin/cape interface, unavailable until sign-in), `runtimes` (managed Java), `safe_archive`, `download_policy`, `webview`, `startup`.
  Preparation (implemented): `mc_meta`, `download`, `java_install`, `natives`, `loader_prepare`, `prepare`, `prepare_cmd`. Planned: `launch` (build the command line from the prepared stores, start the game with the managed Java, track playtime), `updater`.
- Frontend is a thin view layer. It calls typed Tauri commands and listens to events. No business logic, no secrets, no direct file/network access to Mojang/Microsoft APIs. All its text comes from the localization layer (see Localization).
- Tauri commands: small, validated, return `Result<T, E>` where `E` is a serializable stable-code error (`CodedError` and its siblings; never prose for the user, see Localization). Long tasks (downloads, launch) run as tokio tasks and report progress via events/channels, and must be cancellable.
- Keep a single typed IPC boundary on the frontend (`src/lib/ipc/`); never scatter raw `invoke("...")` strings through components. Generate or hand-maintain matching TS types for command payloads.
- Instances live in `instances/<name>/` inside the portable root, each isolated (own `mods`, `saves`, `config`). Shared immutable data lives in the root's `libraries/`, `assets/`, `minecraft/` and `runtimes/` and is content-addressed and downloaded once.

## Security rules (non-negotiable)
- Microsoft auth: OAuth 2.0 device code or PKCE auth-code flow with system browser, then Xbox Live, XSTS, Minecraft services. No embedded webview login, no client secrets in the repo.
- Store refresh/access tokens only in the encrypted portable vault (`vault.rs`). Never use the OS credential store/DPAPI (it is bound to one machine and user, which breaks portability), and never put tokens in plain files, logs, localStorage, or frontend state beyond what the UI needs (profile name, UUID, skin).
- Never log tokens, auth headers, or full launch command lines (they contain the access token). Redact before logging.
- Verify every download against the SHA-1/SHA-256 or size from the manifest/API before use; write to a temp file then atomically rename. Reject mismatches and delete the partial file.
- HTTPS only (rustls). Allow-list hosts for metadata and downloads (Mojang, Microsoft sign-in, loader runtimes: see Product philosophy; no content platforms, ever). Follow redirects only to allowlisted hosts.
- Archive extraction (natives, loader installers, Java runtimes, user-picked archives): guard against path traversal (zip-slip), absolute paths, symlinks escaping the target, and decompression bombs (size/entry limits).
- Launch with `Command::new(java).args([...])`, never through a shell. Treat user-provided JVM args as untrusted input: validate and display them.
- Tauri capabilities: least privilege. Grant per-window permissions in `src-tauri/capabilities/`, no wildcard fs/shell scopes, strict CSP (no `unsafe-eval`), no remote content loaded into the webview.
- Self-update must be a custom signed-zip updater (verify a detached signature with a public key compiled into the binary, then swap files). `tauri-plugin-updater` is intentionally not used: on Windows it launches installers, which a portable build must never do. The signing key never enters the repo.
- Treat version manifests, loader metadata, user-provided version profiles and API responses as hostile. Parse with strict serde types and bounded sizes.
- Run `/security-review` before merging anything touching auth, downloads, extraction, process launch or updater.

## Portability (hard requirement)
**PERMANENT ARCHITECTURAL RULE.** The launcher itself must never intentionally write persistent data outside its own folder, and must never depend on anything installed on the PC (Java, WebView2, VC++ redistributable, .NET, a global `.minecraft`). Any change that would violate this is rejected, not worked around. Stored paths are always relative. Admin rights are never required. Windows' own artifacts (Prefetch, event logs, MuiCache/Jumplist registry entries, SmartScreen/Defender caches) are not ours and must never be "fixed" with OS modifications.

Goal: copy the whole `Clade-Launcher/` folder to a USB stick, plug it into another 64-bit Windows 10/11 PC, run `Clade.exe`, and have accounts, instances, Minecraft files, Java runtimes and settings available with nothing to install or re-download.

Layout (all under the root = the directory containing `Clade.exe`):
`Clade.exe`, `data/` (settings.json, accounts.json, vault.bin, clade.lock, webview2/ profile), `instances/`, `runtimes/` (java/, webview2/), `minecraft/`, `libraries/`, `assets/`, `cache/` (tmp/ for scratch), `logs/`.

### Guarantees and how they are enforced
- **No absolute paths, ever.** The root is found at run time from `current_exe()` (`PortableRoot::discover`). Debug builds use `target/debug/clade-root` so development never pollutes the repo. Stored paths are `RelPath` values: validated, `/`-separated, relative to the root; they reject absolute paths, drive letters, UNC, `..`, backslashes, `:` (ADS), device names (CON, NUL...), trailing dots/spaces and control characters. `PortableRoot::relativize` refuses anything outside the root, so an absolute path cannot leak into a saved file. Loading a settings file with an absolute or escaping path fails.
- **Nothing in `%APPDATA%`, `%LOCALAPPDATA%`, Documents or a global `.minecraft`.** The WebView2 profile is redirected to `data/webview2` (the window is created in code with `data_directory`; the config-file option is always resolved under `%LOCALAPPDATA%` and must not be used, so `tauri.conf.json` has `create: false`). Do not add plugins that default to AppData (`tauri-plugin-store` was removed for this reason). Use `PortableRoot` for every location.
- **Managed Java only.** `runtimes::resolve_java` is the only way to get a Java executable. It never consults `PATH`, `JAVA_HOME`, the registry or Program Files, fails with `Missing` instead of falling back, and re-hashes `javaw.exe` against `runtime.json` (written only after the archive was verified) before returning it.
- **Self-contained game files.** Versions, libraries, assets, natives and instances live in the root. When launching, set `cwd` and `--gameDir` to the instance, `-Djava.io.tmpdir` to `cache/tmp`, natives dir inside the instance/`cache`, and pass the log/crash locations inside the root. Never read or write the global `.minecraft`. Only download when the content is genuinely absent (check the hash, not just existence).
- **Portable encrypted vault** (`vault.rs`, `data/vault.bin`): Argon2id (64 MiB, t=3, p=1; floors 19 MiB/t=2 enforced on read, ceilings 1 GiB/t=16/p=8 against hostile files) derives a 32-byte key from the master passphrase; XChaCha20-Poly1305 with a fresh random 192-bit nonce per save; the whole header is authenticated as AAD; key and secrets are zeroized on lock/drop; the passphrase is never stored; wrong passphrase and tampering are indistinguishable by design; writes are atomic with one `.bak` generation. Account metadata (`accounts.json`) holds names/UUIDs/status only (no tokens) and stays readable while the vault is locked.
- **Expired or revoked Microsoft credentials are a normal state**, not an error: `AccountStatus::NeedsReauth { reason }`. Network failures are not re-auth conditions. Map token-endpoint errors with `classify_oauth_error`.
- **Safe IO:** `fsutil::atomic_write` (temp file + fsync + rename), `install_verified` (size+SHA-1/256 before the file is moved into place, partial files deleted), `reject_links_between` (symlinks/junctions/reparse points), `safe_archive` (zip-slip, symlink entries, case collisions, entry/size/ratio limits enforced while streaming, extraction into scratch then atomic rename), `download_policy` (https only, host allow-list, no userinfo/ports/IP hosts; re-check every redirect).
- **No administrator rights:** the manifest requests `asInvoker`; the executable is never named setup/install/update (Windows would force a UAC prompt). Long paths and UTF-8 are enabled in the manifest.
- **One user of the folder at a time:** `RootLock` holds an OS file lock on `data/clade.lock` (dropped automatically if the process dies or the stick is pulled), so two PCs cannot corrupt the same folder.
- **No installer fallback, no required redistributables:** the release build links the C runtime statically (`+crt-static`, set by `package-portable.ps1` with an explicit `--target` so build scripts are unaffected) and the WebView2 loader is static; verified imports contain no vcruntime/msvcp/WebView2Loader DLLs. The only CRT dependency is the Universal CRT that ships with Windows 10/11.
- **WebView2 is bundled.** The Fixed Version runtime (currently 154.0.4258.53 x64) is shipped in `runtimes/webview2/`. `webview::select_runtime` points WebView2 at it with `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` before any WebView exists, and the profile/crash handler use `data/webview2`. Verified: the launcher's whole WebView2 process tree runs from the folder and uses a profile inside it, even on a PC that also has the evergreen runtime. If neither the bundled nor an installed runtime loads, startup shows a message box and exits; it never downloads or runs an installer. `package-portable.ps1` refuses to build a release zip without it (`-WithoutWebView2` is a clearly named dev-only zip).
- **WebView2 license obligations (accepted by the project owner on 2026-10-04).** The Fixed Version license lets us redistribute the runtime but requires that end users agree to terms protecting Microsoft at least as much, that we obtain it directly from Microsoft, and that we indemnify Microsoft. The license text ships in `licenses/` inside the zip (source: `scripts/licenses/`). SmartScreen is disabled in the WebView by wry's default arguments, so the Section 8 SmartScreen notice is not triggered; if that default ever changes, add the notice to the app. Re-check the license when updating the runtime.

### Release procedure
1. Get the Fixed Version x64 CAB directly from https://developer.microsoft.com/microsoft-edge/webview2/ (accepting its license; keep it in the git-ignored `dist-portable/vendor/`).
2. `scripts/package-portable.ps1 -WebView2Cab <cab>`: extracts it with the system `expand.exe`, **aborts unless `msedgewebview2.exe` has a valid Microsoft Authenticode signature**, builds with `pnpm tauri build --no-bundle --target x86_64-pc-windows-msvc` and static CRT, assembles `Clade-Launcher/`, writes `Clade-Launcher-Portable.zip` and a `.sha256`. Current output is about 297 MB (675 MB extracted).
3. If Windows App Control blocks a build script (os error 4551), `cargo clean --release -p <crate>` and rebuild.
4. Re-run the portability verification below before publishing.

### Portability verification (repeat for every release; last done 2026-10-04, all passed)
1. Extract the zip to a *different drive and path* than the build (a plain new folder; `subst` drives do not work with the `\\?\` paths used by extractors).
2. Snapshot `HKCU\Software` (`reg export`), start a `FileSystemWatcher` over `%LOCALAPPDATA%`, `%APPDATA%`, `%TEMP%`, `%ProgramData%`, Documents, Desktop, Downloads, `~/.minecraft` and the profile root (stop the watchers before draining the queue), then run `Clade.exe`.
3. Confirm the window responds, the log says `webview=Bundled`, and every `msedgewebview2.exe` whose parent is the launcher runs from `runtimes/webview2` with `--user-data-dir` inside `data/webview2`.
4. Seed `settings.json`/`accounts.json`/an instance (relative paths only), move the whole folder to another drive and a path containing spaces, run again, confirm settings and files are intact.
5. Read the watcher log and registry diff: nothing launcher- or WebView2-named may appear outside the folder. Result last time: zero launcher-originated writes; only other applications' files changed.
6. Delete the test folders.

Known OS-level artifacts (not ours, not suppressed): the shell records `Clade.exe`'s path and name in `HKCU\...\Shell\MuiCache`, Windows Search updates `JumplistData` for the WebView2 app id, and Prefetch/event logs may mention it.

### Rules for new code
- Resolve every path through `PortableRoot`; persist only `RelPath`. Never call `dirs`/`directories`, `std::env::temp_dir()`, `std::env::var("APPDATA"|"LOCALAPPDATA"|"USERPROFILE"|"JAVA_HOME"|"PATH")`, or Tauri's `app_data_dir()/app_config_dir()/app_cache_dir()`.
- Scratch files go in `cache/tmp` or a `cache/` subfolder (`tempdir_in`), never the system TEMP. Any child process (loader installers, later the game) is started with a cleared environment plus explicit, verified variables, never by inheriting the user's session; these rules are enforced by `tests/portability_rules.rs`.
- Secrets only through `Vault`. Never `Debug`/log/serialize them elsewhere; keep them out of the frontend.
- Anything fetched from the network goes: policy check, download to `cache/` temp, `install_verified`, then (archives) `safe_archive::extract_zip_atomic`. Never execute or load a file that has not passed this.
- Every on-disk format carries a version; a folder newer than the build is refused (`LAYOUT_VERSION`), never silently rewritten.
- Add a unit test for each new guarantee (see the `moving_the_folder_keeps_stored_paths_valid` and vault tamper tests).

### Unavoidable limitations (be honest about these in the UI and docs)
- **Microsoft may require sign-in again** on any PC (inactive/expired refresh token, password change, revoked session, new-device risk or consent prompt). Portability cannot prevent it.
- **Master passphrase:** a stolen stick allows unlimited offline guessing. Argon2id slows it but cannot stop a weak passphrase (minimum is only 8 characters; encourage long passphrases). Account names/UUIDs in `accounts.json` are not encrypted.
- **The bundled WebView2 runtime is not auto-updated** (Fixed Version runtimes are serviced by the app vendor). Security fixes require re-packaging with a newer runtime. It makes the zip about 297 MB (675 MB extracted) and needs Windows 10 or 11, 64-bit.
- **Not verified on a PC that truly has no WebView2.** Development machine has the evergreen runtime installed (it cannot be removed without admin). Independence is shown by the process tree using only the bundled runtime; a clean-VM test is still recommended before a public release.
- **Windows may still warn:** a downloaded zip carries Mark-of-the-Web and an unsigned `Clade.exe` triggers SmartScreen; Smart App Control / WDAC can block unsigned binaries outright (observed during development). Code signing would reduce this; it is not implemented.
- **Filesystem:** FAT32 cannot hold files over 4 GB and has no atomic-rename guarantees; use exFAT or NTFS. Removing the stick during a write can lose that write (writes are atomic, so files stay consistent, and the vault keeps one `.bak`). Slow USB sticks make first launch and downloads slow. Keep the root path short.
- **Not fully hermetic:** Java itself may touch the registry (`java.util.prefs`) and mods can write wherever they choose; the OS may keep a Prefetch/Recent-files entry and crash dumps for `Clade.exe`. Nothing the launcher controls is written outside the folder, but these side effects cannot be prevented.
- **Antivirus/EDR** on another PC may quarantine or block `Clade.exe` or the runtime.
- **Self-update** while running from a stick must replace files in place; it is not implemented yet and must follow the signed-zip design above.

## Rust quality
- Edition 2021+, stable toolchain. `cargo clippy -D warnings` and `cargo fmt` must pass.
- No `unwrap()`/`expect()`/`panic!` outside tests and provably infallible spots (comment why). Use `thiserror` for library-style module errors, `anyhow` only at top-level glue.

- Do not add a Minecraft launcher crate as a dependency (evaluated: `lyceris`, `daedalus`, `minecraft-msa-auth` are stale, low-adoption or too narrow). Implement against official Mojang/Microsoft formats directly with serde models.
